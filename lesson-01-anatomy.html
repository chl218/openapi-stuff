Anatomy of an OpenAPI contract

Before you generate anything, learn to read the file. Every tool in this course reads the same few top-level sections.

Red arrows are $ref pointers: operations point at shared schemas so you define Book once.

What you will learn

  • The four jobs of a spec: metadata, paths, components, security.
  • Why operationId matters (generated method names).
  • How $ref keeps the document small.
  • The difference between OpenAPI (the standard) and Swagger (the tools and the older 2.0 name).

Concepts

TermMeaning
OpenAPI Specification (OAS)The standard format. Current line is 3.x (3.1 is common; 3.2 is newer). Version 2.0 was called Swagger.
SwaggerTooling: Swagger UI (browser docs), Swagger Editor, Swagger Codegen.
Path itemA URL template such as /books/{id} with one operation per HTTP method.
SchemaA JSON Schema description of a request or response body.
operationIdA unique name per operation. Client generators turn it into a method name.

Run it locally

Exercise Hand-write a small spec for a Library API with two paths, then load it in a viewer. Follow pseudocode/lesson-01-anatomy/README.md. To view it in C#, build the small SpecViewer web project described in viewer.pseudo: dotnet run, then open /swagger on the port the console prints. Editing the YAML and refreshing the page is your feedback loop. (No SDK yet? Paste the file into the online Swagger Editor.)
You are done when The viewer renders both paths with no errors, and you can say which section a given line belongs to.
