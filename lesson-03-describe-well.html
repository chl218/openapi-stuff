Describe the API so consumers need no guesswork

A generated spec is only as useful as the details you give it. This lesson adds every response a caller can get, the rules for each field, and examples.

Left: the operation. Middle: every response a caller must handle. Right: the schemas those responses point to.

What you will learn

  • Declare each possible status code, not just the happy path.
  • Return errors as RFC 9457 Problem Details so every error has one shape.
  • Put rules on fields (required, length, ISBN pattern, year range) so they appear as schema constraints.
  • Add summaries, descriptions, tags, and example values.

Where each detail comes from in C#

You want in the specYou add in code
Response status and body type.Produces<T>(status) or TypedResults return types
Summary / description / tag.WithSummary, .WithDescription, .WithTags
Stable operation name.WithName("createBook")
Required / length / rangeData annotation attributes on the request model
Field docsXML doc comments (enable GenerateDocumentationFile)
Run it locally Extend your Lesson 2 project. Post a book with a blank title and confirm you get a 400 body in Problem Details shape. Then open the UI and confirm that the 400 and 409 appear under POST /books.
You are done when Every operation lists at least one error response, and Book shows length and pattern constraints in the JSON.
